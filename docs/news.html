Un seul concept de rôle

Comment Librairie Crystal est passée de deux systèmes parallèles (type de compte Identity + permissions dynamiques) à un modèle unifié basé sur DynamicRoleId et les permissions configurables.

Le problème Avant / Après Les 6 phases Architecture Impact RH Impact technique Résumé

Pourquoi cette migration ?

L'interface proposait deux champs qui semblaient dire la même chose : Type de compte et Permissions sur mesure. Sous le capot, c'était encore pire : deux couches techniques indépendantes qui pouvaient diverger.

Ce que voyait l'utilisateur RH

  • « Type de compte » : Admin, Gérant, Assistant, Employé
  • « Permissions sur mesure » : liste des rôles dynamiques
  • Confusion : deux listes, souvent identiques

Ce que faisait le système

  • AspNetRoles + claim JWT Role
  • DynamicRoleId + API /me/permissions
  • ~70 endpoints protégés par [Authorize(Roles=…)]
  • Menus gérés par CASL côté frontend
Objectif : un seul champ Rôle dans l'UI, une seule source de vérité en base, une seule logique de sécurité (permissions dynamiques), du formulaire jusqu'à l'API.

Les phases de migration (0 → 5)

Migration incrémentale en six étapes pour éviter de casser l'application en production.

0

Backfill des données

Assigner un DynamicRoleId à chaque utilisateur existant à partir de son rôle Identity. Garantir qu'aucun compte actif ne reste sans rôle dynamique.

DataSeederBackfill
1

UI unique + sync coulisse

Un seul champ « Rôle » dans les formulaires (utilisateurs, onboarding). DynamicRoleId obligatoire côté API ; sync Identity automatique encore active pour compatibilité.

UserFormUserService
2

Permissions unifiées API

Remplacement de tous les [Authorize(Roles=…)] par [RequirePermission]. Enrichissement des presets (Gérant, Assistant, Employé). Sync des permissions preset au démarrage.

ControllersPresetRolePermissions
3

Frontend découplé du JWT

SessionUser sans champ role. Menus et boutons via CASL uniquement. usePermissions remplace les checks Admin/Gérant.

AuthContextCASL
4

Suppression Identity sync

Fin de SyncIdentityRoleAsync, retrait du claim Role du JWT, DynamicRoleId NOT NULL en base (migration EF). Register et Login alignés.

AuthServiceMigration EF
5

Nettoyage final

Suppression du code mort (devAuth, isUserRole, champ User.role). Seed sans AspNetRoles. Doc RH et test E2E création utilisateur avec sélection de rôle.

CleanupPlaywright

Ce qui change pour l'équipe RH

Plus simple

  • Un seul champ à remplir : Rôle
  • Liste unique : presets + rôles personnalisés
  • Fiche utilisateur affiche le nom du rôle dynamique
  • En-tête : « Rôle : Gérant » depuis l'API, pas le JWT

Inchangé dans l'esprit

  • Les 4 profils standards gardent les mêmes droits métier
  • Les rôles custom restent dans Rôles et permissions
  • Comptes de test identiques (admin@, gerant@, etc.)
  • Mot de passe seed : ValidPass1!a

Ce qui change pour les développeurs

Backend (.NET)

  • ApplicationUser.DynamicRoleId requis
  • UserResponse : plus de Roles[]
  • LoginResponse : dynamicRoleId
  • Migration : DynamicRoleIdRequired
  • SeedUsersAsync sans AspNetRoles

Frontend (React)

  • SessionUser sans role
  • userMapper : payload dynamicRoleId seul
  • PRESET_ROLE_IDS pour les couleurs / libellés
  • usePermissions(ENTITY) partout
  • Fichiers legacy supprimés (devAuth, isUserRole…)
Déploiement : en développement, les migrations s'appliquent au démarrage de l'API. Sinon : dotnet ef database update --project Crystal.Infrastructure --startup-project Crystal.API depuis le dossier backend/.

En résumé

La migration élimine la dualité « type de compte » / « permissions sur mesure » au profit d'un rôle unique dont les droits sont configurables et cohérents de la base de données jusqu'à l'interface.

Bénéfices

  • Moins de confusion pour les gestionnaires RH
  • Sécurité centralisée sur les permissions
  • Rôles custom sans bricolage Identity
  • Tests et E2E alignés sur le modèle réel
